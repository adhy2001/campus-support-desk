# Campus Support Desk — Student Support & Ticket Management

Prototype for the Edumerge pre-drive assignment (Assignment 4).

## Setup

```bash
npm install
npx prisma migrate dev --name init
npm run seed
npm run dev
```

Open http://localhost:3000

- **/student** — raise a ticket, view your own tickets (per-student view with status/priority/overdue badges)
- **/staff** — full Kanban board across all 6 statuses: filter by category, assign staff, move status, escalate tickets, see SLA/overdue/auto-escalate flags
- **/admin** — KPI stats, bar-chart breakdowns by category and staff workload, status breakdown, SLA breach report
- **/tickets/[id]** — full ticket detail: description, SLA due date, comments thread (commenter selectable), activity/audit timeline

## Deploy (optional, for a live link)

```bash
npx vercel
```

> **Note:** SQLite resets on Vercel's serverless filesystem between deploys. For a persistent live demo, swap `DATABASE_URL` to a hosted Postgres (e.g. Neon or Supabase) — the Prisma schema needs zero changes, only the `datasource` provider becomes `postgresql`.

## Design decisions (for the approach note)

- **SLA hours vary by category** (`lib/ticketLogic.ts`) — certificates (96h) legitimately take longer than ID card reissues (72h) or fee queries (24h). This reflects how these requests are actually handled in real institutions rather than treating all tickets the same.
- **Overdue and auto-escalation are computed on read**, not stored — so they're always accurate without a background job. A ticket is "overdue" if it's still open past its SLA date; it's flagged for auto-escalation if it's URGENT priority, unassigned, and already overdue.
- **Status transitions are validated server-side** (`isValidTransition`) — a ticket can't jump straight from OPEN to RESOLVED, enforcing that someone actually worked on it (IN_PROGRESS) first. Reopening from RESOLVED/CLOSED is allowed, since real support tickets do get reopened.
- **Every state change writes an immutable Activity row** — assignment changes, status changes, priority changes, comments, and escalations are all logged, giving management visibility and an audit trail without extra tooling.
- **Kanban board on the staff dashboard** groups tickets by all 6 statuses (OPEN, IN_PROGRESS, PENDING_STUDENT, ESCALATED, RESOLVED, CLOSED) so staff can see queue depth at a glance, with SLA/priority/escalation badges surfaced directly on each card rather than buried in a detail view.

## Known limitations / what's next with more time

- No real authentication — role is selected via a dropdown for demo purposes. Production would need proper login + session-based role enforcement.
- SQLite is used for zero-setup local development; production would move to Postgres (schema change only, no code change).
- No notifications (email/SMS) on assignment or SLA breach — would be the next feature to add.
- No automated tests included given the time window; `lib/ticketLogic.ts` is written as pure functions specifically so it's easy to unit test later.
